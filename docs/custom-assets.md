# Shipping our own 3D assets

The mod can ship its own meshes. The whole chain is Blender → FBX → `rc.exe` → `.cgf`,
and every piece of it is already on this machine.

## What makes it possible

`rc.exe` — the game's own resource compiler — comes with the **KCD2 Modding Tools**, a
separate free Steam app for anyone with a KCD2 key. It is already installed here as
`KCD2Mod`, the same build `PackageModDev.bat` deploys to:

```
C:\Program Files\Steam\steamapps\common\KCD2Mod\Tools\rc\rc.exe
```

It loads `ResourceCompilerFBX.dll`, so it takes **FBX directly**. The BCry exporter addon
and its Blender 4.3 requirement are not needed — Blender 4.1's built-in FBX export is
enough, driven headless.

The chunk file version it writes (`0x746`) is byte-for-byte the version the shipping
assets use, so the compiler is the right one.

Also in the tools, worth knowing about: `KCD2Mod\Data\objects\enviro_asset_template\`
holds Warhorse's own example assets — `Assets_Template.max`, four reference `.cgf`s with
their `.mtl`s and source `.tif` textures, and `.cgf.dfp` property sidecars (shadow, LOD
and collision-class flags).

## Building

```
powershell -ExecutionPolicy Bypass -File .\assets\build_castle_wall.ps1
```

Three steps per piece: [`assets/blender/castle_kit.py`](../assets/blender/castle_kit.py)
builds the mesh and writes an FBX, `rc.exe` compiles it, and the `.cgf` is copied into
`data/Objects/mercenaries/walls/`. It builds seven: three wall variants, three corners
and the tower (the table below).
`PackageMod.bat` zips the whole of `data/`, so they ship from there with no packaging
change.

The model is generated by script rather than saved as a `.blend`, so the dimensions are
readable and a change is a one-line edit and a rebuild.

## The traps, in the order they cost time

**`/mergeallnodes`, not `/mesh_merge_nodes`.** RC silently ignores unknown switches, so
the wrong name looks like a flag that does nothing. With merging left on (the default)
the object's name is replaced by `Merged`.

**`/mtl` does nothing on the FBX path.** The help says it takes a material path without
the extension, but the compiled CGF's material library is always `default` — with the
switch, without it, and with a `.mtl` sitting beside the FBX. The submaterial name from
Blender (`wall`) *is* preserved.

So the material is applied at spawn instead: a wall type carrying `mtl` gets
`ent:SetMaterial(...)` in `WallSpawnSegment`. Base-game meshes leave it nil and keep
their own material.

**The FBX path emits fewer chunks than a shipping asset.** Ours has no `4110`, `4115` or
`4120` (node) chunks, which looks broken next to `wall_segment_220_60_a_a.cgf`. It is not
ours: decompiling a *shipping* asset with `/cgftofbx` and recompiling that FBX produces
exactly the same reduced structure. It is what RC's FBX importer does.

The shipping assets differ for a second reason too - `RCJob_WH.xml` compiles them with
`SplitMeshFile="1"` and `StripMesh="1"`, which moves the geometry out to a `.cgfm`
companion and leaves the `.cgf` a few KB of structure. Ours keeps its geometry inline.

### Three ways Blender booleans destroy the mesh

All three cost a full iteration each, and all three fail *silently* - the build succeeds
and the model is simply wrong.

1. **The FAST solver leaves the cutter behind.** Every opening comes out as a flat dark
   patch with stray faces beside it, and the object's bounding box is far bigger than its
   dimensions - the giveaway. Use `EXACT`.
2. **EXACT deletes whole shells if the TARGET is not one closed solid.** The kit is built
   from interpenetrating boxes; handed that pile, EXACT resolves it as a single CSG solid
   and drops the shell being cut. That is why the wall body vanished from every render
   while its trim survived. `cut_solid()` exists for this: it cuts one clean box on its
   own, and assembly happens afterwards.
3. **EXACT annihilates the target if the CUTTER is not one closed solid either.** An
   arrow loop is a slit plus a cross-bar plus a splayed embrasure - three overlapping
   boxes. As one cutter object that is self-intersecting, and the result is a mesh with
   **zero** polygons. So `arrow_loop()` returns its boxes as a list and `cut_solid()`
   applies one boolean per box.

A fourth, related trap has nothing to do with booleans: **a proxy face exactly coincident
with a visible one is fatal.** The weld in `finish()` collapses the pair into one face and
the Nodraw material can be the survivor, which deletes that piece of wall from the render
and would make it invisible in game. `Builder.pbox()` holds the collision hull
`PROXY_EPS` (12 mm) inside the surface it stands for.

The cheap check for all of this is a face count per material slot, and the build prints
one per piece and REFUSES to continue if a slot that should carry geometry carries none:

```
[slots]  a         {'wall': 1326, 'quoin': 174, 'allure': 5, 'trim': 48, 'proxy': 12}
[slots]  tower     {'wall': 4747, 'quoin': 714, 'allure': 12, 'wood': 161, ...}
```

It is there because three separate details have silently failed to build in this kit's
history - a boolean that ate its target, a quoin chain built at the corner's centre
instead of its arris, and an edit that targeted a line the file no longer contained, so
the code was written but never called. Every one survived a full render and an art
review before anyone noticed. A slot count would have caught all three in seconds.

**Collision comes from a Nodraw submaterial, not from the render mesh.** A spawned prop
has no collision of its own; `mercenaries_Prop` physicalises PE_STATIC only when the
`.cgf` carries a physics proxy. The base game encodes that as a submaterial with
`Shader="Nodraw"` and a `SurfaceType` (`wall_segments_220_60_a.mtl` calls it `proxy`) -
faces assigned to it never render and become the collision hull.

So each piece has two material slots and **the order is the contract**, because a slot
maps to a submaterial by index:

| slot | submaterial | what it is |
| --- | --- | --- |
| 0 | `wall` | the visible stone |
| 1 | `proxy` | `Nodraw`, `SurfaceType="mat_rock"` - the collision hull |

The wall's hull is the curtain up to the walkway plus a solid rail along the parapet
line, so the allure is something you can stand on and the crenels are not holes to fall
through.

**One VISIBLE material.** A `.cgf` holds a single mesh, and a second *drawn* material
assigned to some vertices does not render — which is what the modding wiki's "1 material"
rule means. A `Nodraw` proxy alongside it is fine, and is how the base game does it. The
generator joins everything into one object with the two slots above.

**Confirmed in game.** The wall renders, tiles and is built with; the missing node chunks
turned out not to matter.

## The material

[`merc_castle_stone.mtl`](../data/Objects/mercenaries/walls/merc_castle_stone.mtl) is
plain XML and shared by both pieces: submaterial `wall` lifted from
`wall_segments_220_60_a.mtl`, then the `proxy` Nodraw hull. It points at the base game's
own stone set:

```
textures/structures/walls/stone_wall/wall_b_4x4_diff.tif
textures/structures/walls/stone_wall/wall_b_4x4_ddna.tif
textures/structures/walls/stone_wall/wall_b_4x4_displ.tif
```

Nothing but the `.cgf` and this file is shipped — no textures. `wall_b_4x4` tiles over 4 m,
which is why the wall segment is 4 m long and the UVs are a cube projection at
`cube_size=4.0`: one texture tile per segment, at the scale the artists authored it.

## The pieces

Seven, all built by `assets/blender/castle_kit.py` and sharing one `.mtl`:

| piece | size | what it is |
| --- | --- | --- |
| `merc_castle_wall_a/b/c` | 4.00 x ~2.5 x 6.77 m | the curtain, three variants |
| `merc_castle_corner_45/90/135` | 3.1-4.2 m | turns the run without needing a tower |
| `merc_castle_tower_a` | 6.72 x 6.14 x 10.09 m | enterable, two stages: door, stair, walk-level doorways, vice, fighting platform |

Shared heights are the point of the kit: `WALK_Z` (4.90 m) is the wall walk, the tower's
first floor **and** the sill of the doorways through the tower, so a walk runs unbroken
from a wall through a corner, through a tower and out the other side.

**The wall.** 4.00 m exactly, so `len = 4.00` is not a guess and a run tiles with no
seam. Nothing may overhang the tile edge, which is why the plinth batters only across the
thickness and the merlon caps are clamped - but the continuous courses deliberately run
12 mm PAST it, so consecutive segments interpenetrate instead of meeting cap to cap. Two
bevelled end caps butted together leave a hairline groove at every joint and the run
reads as bolted-on panels; the overlap is buried inside the neighbour, so nothing
z-fights. 1.80 m thick leaves 1.30 m of walk behind a 0.50 m parapet.

**The crenellation is not a variant.** Every segment and both corner arms carry the same
1.00 m period and the same full set of merlons, and the corner's arris is a solid
L-shaped block rather than a crenel. Phase shifts between neighbours, or a deliberately
missing merlon, are the first thing the eye picks up along a run. Variation lives only in
things that do not break the line: arrow-loop positions, putlog holes, and how deep the
buttress is.

**The material break is horizontal, not scattered.** The foundation is its own coarser,
browner masonry with a chamfered dressed course at its head. Panels of contrasting stone
part-way up the face read as damage decals; a different footing reads as how the thing
was built.

**Relief is what stops it reading as a box.** The parapet oversails the wall face by
0.12 m on a corbel table - 0.26 m blocks every 0.50 m, a step that divides the tile so
the row runs unbroken across joints - and a buttress stands at the CENTRE of every
segment, alternating deep and shallow along the run. On the joint a buttress advertises
it; at the centre the joint falls in the blank bay between two, and alternating the depth
stops four identical piers reading as corduroy.

**Every external corner is quoined.** Alternating long/short dressed blocks, 0.42 m
courses standing 0.07 m proud of both faces, up the wall corner piece's arris and all
four of the tower's. A rubble-to-rubble mitre is the one thing no real Bohemian castle
corner has, and it is the first place a player looks.

**The corners.** Two wall stubs of the same cross-section meeting at the turn, with an
alternating quoin chain up the outer arris. `merc_wall_angle` snaps the builder's corners
to 45-degree multiples off the run's first edge, so these three cover every corner it can
make (180 being a straight segment). Each stub is `CORNER_ARM` = **2.00 m**, half a
segment: a corner then eats exactly one 4.00 m tile out of the run, which leaves the rest
of the edge a whole number of segments and puts the arm's merlons on the same 1.00 m grid
the segments use. Get that number wrong and every corner in the castle shifts the
crenellation out of phase for the whole run after it — see [castle.md](castle.md) for the
placement side of it.

**The tower.** 4.80 m square outside, 3.56 m clear inside, 8.20 m to the platform: a
room that gets its presence from height, not girth. Stage one is the ground chamber - a
1.20 x 2.20 m door with recessed jambs, a flat lintel and a segmental relieving arch of
seven radial voussoirs (`Builder.ybox`, a box pitched about Y), two timber flights to the
first floor. That floor is a 0.30 m slab on a corbel course at `WALK_Z`, and the wall walk
passes THROUGH the tower by 1.10 x 2.20 m dressed-jamb doorways in all four faces, so the
piece works whichever way it is turned. Stage two is the fighting platform, reached by a
vice in one corner: twelve stone wedge treads (`Builder.prism`) stacked into a solid
helix round a 0.30 m newel that ends in a capstone, with a kerb round the open well. The
platform's parapet stands on a two-step corbel table projecting 0.62 m, and because the
parapet is only 0.36 m thick the 0.26 m gap between wall face and parapet is a real
machicolation, slotted between the corbels. Arrow loops everywhere open in two steps
from a 0.12 m slit to a 0.60 m embrasure inside (`arrow_loop(inner=...)`). Its plinth is
laid as four runs rather than a ring so the door side can be split around the opening -
left whole it stands 0.75 m across the threshold and the player has to climb it to get in.

## How it was tuned

Each iteration renders twelve angles with the game's own textures
(`assets/blender/preview.py`) and hands them to a separate judging agent scoring 0-10
against a KCD2 rubric. That loop is what caught the boolean failures above - the wall
body was simply absent from a render and no amount of reading the code showed it - along
with a quoin chain that was being built at the corner's centre, buried inside 1.8 m of
masonry, and a plinth that ran straight across the tower doorway.
